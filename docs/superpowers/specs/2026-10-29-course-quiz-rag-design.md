# course-quiz-rag — design

Date: 2026-10-29

## Goal

A public Streamlit demo, deployed on the author's VPS via Dokploy, where a visitor uploads a course (PDF) or picks a sample course and gets an interactive quiz generated by a RAG pipeline. The demo must show a recruiter, in under a minute, that this is a real RAG (retrieval over the course, sources displayed) and not a plain LLM call. The site also displays the RAG architecture.

Success criteria:
- Upload a PDF, choose exercise type / level / number of questions, get a playable quiz with a score.
- Every question shows the course passages (with page numbers) that inspired it.
- A tab shows the RAG architecture with the real parameters and, after a generation, the retrieved passages and the prompt sent.
- The public demo stays usable when the LLM quota or a usage limit is reached (pre-generated fallback).
- Runs from one Docker container; the API key is never in the repo.

## Constraints and decisions

- Repo renamed `edu_ai-rag` -> `course-quiz-rag` (done on GitHub).
- LLM: author's OpenCode Go subscription, through its OpenAI-compatible endpoint (`https://opencode.ai/zen/go/v1`, key in `OPENCODE_API_KEY`), using the `openai` Python client. Base URL and model are env-configurable (`LLM_BASE_URL`, `LLM_MODEL`). The exact model is chosen at implementation time by listing `/v1/models` (needs the author's go-ahead to use the key). The docs and third-party sources disagree on base URL form and model list, and none of it has been verified against the live API.
- Quota exhausted or usage limit hit: serve pre-generated sample quizzes with a visible banner.
- Embeddings: MiniLM (sentence-transformers `all-MiniLM-L6-v2`), as in the existing notebook. Vector store: Chroma, in memory, one collection per session.
- Bugs of the previous notebook/API that this design fixes: the correct QCM answer was never parsed; the chosen theme was ignored (`'general'` always sent); retrieval used the whole prompt instead of the theme; `gpt-3.5-turbo` obsolete.

## Structure

```
app.py                 Streamlit entrypoint, 3 tabs: Quiz, Architecture du RAG, A propos
rag/
  ingest.py            PDF -> pages -> chunks -> embeddings -> Chroma collection
  retrieve.py          theme -> top-k passages with page numbers
  generate.py          prompt + LLM call (JSON output) + Pydantic validation
  limits.py            per-visitor and daily caps (SQLite)
  config.py            env-driven settings (chunk size, k, model, caps)
samples/               2 sample course PDFs + pre-generated fallback quizzes (JSON)
tests/                 pytest
Dockerfile, README.md, requirements.txt (minimal, UTF-8)
notebooks/rag.ipynb    kept as the original exploration
```

Each module has one purpose and a plain-function interface; `generate` depends on `retrieve` output only, and the LLM client is injected so tests use a fake.

## Data flow

1. Upload (or sample pick): PDF checked against max size (default 5 MB) and max pages (default 40); rejected with a clear message otherwise.
2. `ingest`: extract text per page, split into chunks (default 800 chars, 100 overlap, configurable), embed, store in a session-scoped Chroma collection with `page` metadata. Text-less (scanned) PDFs are detected and refused.
3. User picks exercise type (QCM or analysis exercise), level, number of questions (1-10) and a theme (free text; or "whole course").
4. `limits` check. If blocked -> fallback quiz from `samples/`.
5. `retrieve`: query = the theme, top-k passages (default 6) with page numbers.
6. `generate`: prompt built from the passages; LLM asked for JSON matching a schema: list of `{question, choices[4], correct_index, explanation, source_chunk_ids}`. Validated with Pydantic; one retry on invalid JSON; on second failure show an error, no crash.
7. UI renders an interactive quiz: answer selection, per-question feedback with explanation and the source passages (page + text), final score.
8. The Architecture tab renders the pipeline diagram with the live config values; after a generation it also shows the retrieved passages and the prompt used.

## Architecture tab

Diagram of: PDF -> parse -> chunk -> embed (MiniLM) -> Chroma <- theme query -> top-k -> prompt -> LLM (OpenCode Go) -> JSON -> quiz. Drawn as inline SVG/Graphviz in the Streamlit page. Parameters shown come from `config.py`, so the page cannot drift from the code. Short text under each stage says what it does and why.

## Limits and cost guards

- Max PDF size and pages (above).
- Per visitor (session id + IP hash when available): default 5 generations per day.
- Global: default 100 generations per day.
- All caps env-configurable. On any cap, or on an LLM error that looks like quota exhaustion (HTTP 429 / quota message), switch to fallback quizzes with a banner.
- Uploaded PDFs are held in memory for the session only, never written to disk, never logged.

## Error handling

Invalid or oversized PDF, scanned PDF, empty theme match, invalid LLM JSON (retry once), LLM timeout/error, quota exhausted: each produces a user-facing message; none crashes the app.

## Testing

pytest, LLM faked:
- chunking (sizes, overlap, page metadata)
- retrieval uses the theme, not the whole prompt
- JSON parsing/validation including the correct-answer case that the old parser dropped; invalid JSON retry
- limits (per-visitor, daily) and fallback switch
- config values reflected in the Architecture tab data
Manual check of the Streamlit app in the browser before declaring done.

## Deployment

Dockerfile (python slim, MiniLM model pre-downloaded at build to avoid cold start), exposes the Streamlit port. Deployed through Dokploy from the GitHub repo; `OPENCODE_API_KEY` and caps set as Dokploy env vars. SQLite file for caps on a mounted volume.

## Out of scope

User accounts, persistent storage of courses, multi-file upload, other languages than what the LLM handles by default, any fine-tuning.
